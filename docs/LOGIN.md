# Shared login presentation (5.0 stable contract)

Hosts opt in with `data-core-login` on a `main`, `section` or other container. Use a `.kn-core-login-card` containing `.kn-core-login-heading` and `.kn-core-login-content`. An optional `.kn-core-login-provider` contains the host's anchor or button with `data-core-login-provider` and the label **Login with KagNode**. The server adapters provide the same structure as the `login-frame` template with `product`, `heading`, `description`, `content` and `provider` slots. Slots are trusted, already escaped authorized markup, as with existing templates. Escape product text for both HTML text and attributes.

Keep existing local forms, validation, CSRF, authorization and local password or vault-unlock steps. Omit the provider slot when the administrator has disabled the connection. Core supplies presentation only: the host must choose an authorized local initiation route and own its pending, cancellation and error handling. Use `data-core-login-status` with `role="status"` for progress/cancellation and an appropriate alert for errors. A button may initiate a CSRF-protected POST; an anchor may navigate to an authorized local route. Never put secrets, exchange results or remote tokens in markup or URLs.

The adapter bundles this CSS with the application's local Core assets. No browser request to GitHub is needed. The shared frame works without JavaScript, preserves local login when the issuer is unavailable, uses 8px controls and 12px cards, and respects reduced motion.

For account menus, supply an authorized `#account-menu` or `[data-core-menu-content]` containing the host's permitted actions. Otherwise Core creates an identity, account/preferences link and existing lock/sign-out action. Set `data-core-settings` on `body` to the host's actual settings destination. `KagNodeCore.setSession({authenticated, subject, name, email})` updates the generated identity on the next open. Profile/account synchronization remains a host responsibility. Never send private destinations to unauthorized clients.

`KagNodeScroll.refresh(container)` optionally limits discovery to a changed subtree; omitted containers retain full-document discovery. Refreshes are batched on the next animation frame. Existing regions repaint together, preserving native scrolling and rails; no waiting timer is inserted. Core's sidebar uses scoped refreshes because its changes do not require rediscovering unrelated page content.

## Optional connection controller

Apps that want the shared code/approval/cancel presentation provide `window.KagNodeLoginHost` with synchronous `state(): {enabled: boolean}`, async `request(action, data)` and async `complete(result)`. The controller is delegated and supports late host initialization; call `KagNodeLogin.refresh()` or dispatch `kagnode:login-ready` when cached state changes. It only binds buttons with `data-core-login-provider` inside a login container with a `data-core-login-status` output. Anchors retain ordinary navigation.

`request('start', {})` returns `{pending: true, attempt_id, user_code, verification_uri, interval, expires_in}`. Core displays the user code as text and the HTTPS verification link, then calls `request('status', {attempt_id})` at the bounded interval. Pending responses continue polling; `{authorized: true, ...}` is passed intact to `complete(result)`. The host owns the signed-in, local-unlock or setup continuation. Completion disables another start on that button. The host can call `KagNodeLogin.reset(buttonOrContainer)` to clear that completion and status when returning from local unlock/setup to login; reset cancels an active attempt, ignores its late results and rechecks cached enabled state. Cancellation calls `request('cancel', {attempt_id})`, restores focus and ignores late results. Polling expires after the host lifetime (at most ten minutes), uses intervals from one to thirty seconds, and stops on page exit. Timeout, reset and page exit best-effort cancel a known attempt through the host adapter; the backend must still enforce its own expiry. Failed requests present a retry/local-login message without exposing exception details.

The host request adapter owns CSRF, authorized local endpoints and interpretation of backend errors. Attempt identifiers are local opaque handles. Device proofs, exchanged authorization, refresh credentials and account tokens stay on the backend. `state()` only controls presentation; backend authorization remains authoritative. Provider cancellation does not modify the existing local form.

## One frame across applications

The `login-frame` template now owns the KagNode symbol, header, spacing, field skin, labels, primary/secondary buttons, notices and provider divider. Hosts must remove competing auth card, grid and field-skin CSS instead of overriding Core. Keep form IDs, names, CSRF fields, autocomplete attributes and all authorization behavior. Group a label/control/helper in `.kn-core-login-field`, mark a primary continuation with `data-core-login-submit`, and group recovery/signup links in `.kn-core-login-links`. Notices remain inside `content`; optional `provider` markup is omitted when disabled. The frame is the same for sign-in, recovery, MFA and local vault/mailbox continuation; the host supplies the truthful heading and required controls.

Signed-out appearance follows the system; there is no theme button in the login frame. Account/settings remains the appearance editor. Required local authentication does not become optional when KagNode confirmation succeeds. Logos is account-free.

The `login-field` template accepts trusted `label`, `control` and `help` slots. The `login-secret` template accepts trusted `control` and `action` slots, placing a password input and a labeled `type="button"` reveal control in one shared 44px row. Hosts keep their existing reveal handlers, IDs and autocomplete semantics. Use `.kn-core-login-check` for a checkbox with wrapping text. These classes avoid app-specific password/checkbox layout overrides.

## Progressive local sign-in (5.0.5)

Add `data-core-login-progressive` to the existing native sign-in form inside the canonical frame. Core shows the existing identity/email field first, then the existing password field after **Continue**. The latter view shows the entered identity and a **Change** button. There are no numbered steps and no account-existence request. The actual sign-in submission and any subsequent MFA, vault unlock or mailbox credentials remain host-owned.

Only enabled controls participate in eligibility; disable unused confirmation fields during sign-in and restore them during setup. Eligibility requires one identity field (`data-core-login-identity`, `autocomplete="username"`, `autocomplete="email"` or `type="email"`) and exactly one password field. Password-change, new-password and standalone one-time-code forms are not enhanced. A combined legacy sign-in may explicitly wrap its password and mandatory OTP fields in `data-core-login-credentials`; Core reveals that whole group together after identity and preserves the same authenticated POST, without pretending that an extra authentication phase occurred. OTP outside this explicit group prevents enhancement. Single administrator-key/password-only forms stay single credential. Existing unmarked sign-in forms are enhanced only when the secret explicitly uses `autocomplete="current-password"`; `data-core-login-progressive="off"` opts out. Mark new-password fields correctly, and never use the sign-in opt-in on registration or password-change forms.

Keep native `action`, `method`, field `name`, labels, autocomplete and CSRF inputs. Prefer `.kn-core-login-field` and `.kn-core-login-secret` groups; Core can group separate labels and controls without duplicating inputs. Fields stay in the original form and are never disabled or copied into storage. Autofill values and password-manager native submission remain usable. Identity-stage Enter/Continue validates only that control locally; the final submit restores the form's original validation behavior. Without JavaScript, all original controls and normal local submission remain available. A server-rendered failed-password page may add `data-core-login-stage="password"` so users do not repeat identity entry. Existing MFA-only continuation pages use the same frame without progressive treatment.

Field changes use a 150ms fade with a four-pixel entrance; the login card uses a 160ms fade. Both stop for reduced motion. No page-wide parallax, forced scrolling or continuously running login animation is introduced. Call `KagNodeLogin.refresh()` after adding eligible forms dynamically.

## Browser authorization and callback resume (5.0.5)

The existing host interface also accepts a browser start response:

```js
{ pending: true, attempt_id: "opaque-local-handle",
  authorization_uri: "https://nebulacoder.com/…", expires_in: 600 }
```

Core navigates the same tab immediately, without showing a device code. The authorization URL must use HTTPS, contain no user information or fragment, and match the exact origin from trusted `KagNodeLoginHost.issuer` or `host.state().issuer` (default `https://nebulacoder.com`). Those are trusted host configuration, never values copied from query parameters. Core does not cancel this deliberately redirected attempt on page exit or reset. Failed navigations retain local sign-in. Old `{user_code, verification_uri, ...}` responses continue using the existing device-code presentation and bounded polling.

The application callback must validate issuer, state, its browser-bound cookie and its existing pending local attempt; retain any authorization code, verifier and tokens server-side; then redirect to its clean local login route with only `?kagnode_attempt=<opaque-local-handle>`. An optional `kagnode_error` indicates failure but its untrusted text is never displayed or exchanged by Core. No OAuth code, token, email or credential belongs in that browser return parameter. Duplicate or invalid attempt parameters are rejected.

The synchronous Core theme bootstrap removes both callback parameters using `history.replaceState`, preserving unrelated query parameters, fragment and history state, and keeps the opaque handle only in this document's memory. Standard adapters place this bootstrap first in the head, before application code and Core's deferred UI. Applications embedding assets manually must retain that order; login.js has a fallback scrub for existing manual embeddings. This cannot erase the original server request or previously loaded resources; callbacks must already have removed sensitive issuer parameters. The handle is never persisted in browser storage.

After asynchronous cached-session/availability initialization, the host calls `KagNodeLogin.refresh()` or dispatches `kagnode:login-ready`. Core then calls only `host.request('status', {attempt_id})`, followed by `host.complete(result)` for an authorized result. It never restarts the attempt or asks again for a previously confirmed administrator key. `state().ready === false` defers resumption; `ready: true` also supports hosts initialized before Core loads. Calls made during resumption do not start another status request. Pending statuses use bounded polling for up to 30 seconds; server expiry and one-use consumption remain authoritative.

`KagNodeLogin.hasPendingReturn` is true while waiting or resuming. Initial cached-state rendering must not reset a pending browser return. An explicit local sign-in, logout, account-policy change or user cancellation should call `reset()` to invalidate it; late status results are ignored. Hosts must also guard asynchronous `complete()` against their own session/epoch changes. A failed, expired or disconnected KagNode flow does not replace or disable the local form. Raw query errors and exception details never enter the UI; the local backend owns the safe outcome and any error-specific explanation.

Provider completions that fill a confirmed identity may call `KagNodeLogin.advance(form, {focus: true})` to reveal and focus the existing password control without submitting. It returns false for ineligible or locally invalid forms. `refresh()` also reveals the password for a populated read-only identity; no useless Change action is shown in that case. When a host reuses a form for initial setup, set `autocomplete="new-password"` and refresh: Core removes progressive controls and restores the original form validation and full fields. Repeated mode changes do not accumulate listeners or controls.
